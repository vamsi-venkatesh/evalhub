# Eval Hub — Phase 4 addendum (shadow · canary · reports · public methodology)
Extends V0–V0.3. Items 15, 16, 17, 18 of the founder's 18. Same auth/JSON/never-lie laws.

## Honest scoping FIRST
This estate runs ONE box per product. "Shadow deployment" and "canary release" as the industry
uses them assume a fleet and a load balancer. We do not have those, and a page claiming otherwise
would be the exact dishonesty this platform exists to prevent. What we CAN do, and will:
  · SHADOW = REPLAY. Sampled REAL past requests are re-run against a candidate build on a second
    port; outputs are diffed and scored; nothing is served to a user. LLM spend is capped.
  · CANARY = BLUE/GREEN + COHORT. Two systemd units; the proxy routes a cookie-pinned share of
    traffic to green; the hub watches green's error rate and eval scores and flips back on breach.
Both names appear on every artifact WITH that definition attached. Never the bare word.

## 15) Shadow replay
- Table shadow_runs(id, target, candidate_sha, baseline_sha, sampled int, compared int,
  diffs int, mean_score_candidate numeric, mean_score_baseline numeric, spend_usd numeric,
  started_at, finished_at, notes jsonb).
- POST /api/shadow/runs {target, candidateSha, baselineSha} → {runId}
- POST /api/shadow/runs/:id/pairs {pairs:[{caseId, baselineOutput, candidateOutput, scores?}]}
  → the hub scores each pair (metrics.embedSim + exactNorm) and records a diff when
  embedSim < EVALHUB_SHADOW_SIM (default 0.90).
- POST /api/shadow/runs/:id/finish → verdict {ok, diffs, diffRate, meanDelta, spendUsd,
  recommendation: "safe"|"inspect"|"block", reason}. Rule v0: diffRate > 0.15 → inspect;
  meanDelta < -1.0 → block; else safe. Thresholds stated in the response, never implicit.
- Conxto side: scripts/eval/run-shadow.mts replays the golden suites against a candidate build
  reachable at CONXTO_CANDIDATE_URL; refuses to run without it. Real user data is NEVER replayed
  in v0 — golden cases only — and the artifact says so.

## 16) Canary + automatic rollback
- deploy/canary.md + scripts/canary.sh in the CONXTO repo (not the hub): blue/green systemd units,
  Caddy cookie-pinned cohort (EVALHUB_CANARY_PCT default 5), and a watcher that calls
  GET /api/gate/:target plus the service's own health, and runs `canary.sh rollback` on breach.
- Table canary_events(id, target, sha, phase 'start'|'promote'|'rollback', pct int, reason,
  created_at). POST /api/canary/events records each transition; GET /api/canary/:target lists them.
- ROLLBACK MUST BE PROVEN, not asserted: the acceptance test deliberately breaks green and shows
  the watcher flipping traffic back, with the events table as the receipt.

## 17) Stakeholder report
- GET /api/report/:target?sha=&format=json|md → a release report: suites with score/baseline/delta,
  regressions caught, latency percentiles, judge calibration state, alerts opened/closed since the
  previous baseline, cost since the last report, and an explicit "what this does NOT cover" block.
- scripts/report.mts writes it to a file for pasting into the vault change log.
- The report NEVER prints a bare "PASSED"; it prints what passed, over what, measured when.

## 18) Public methodology
- A public page at vvdexops.com/evals (static, generated) describing: what a golden suite is here,
  how baselines are promoted, what the judge is and that it is calibrated by kappa against human
  labels (with the current kappa or "uncalibrated"), what the safety probes do and do NOT prove,
  and a FAILURES section listing real misses this platform made — including: the tautological
  assertion the golden generator caught in our own test; the hallucination checker that passed
  mocks then flagged 16/16 clean controls; the safety checker scoring a crisis response as
  compliance; the agent answering implicit suicidal ideation with funnel advice.
- Generated by scripts/methodology.mts in the hub repo from live hub data where numbers appear;
  no number is typed by hand. Published via the existing seo-lab/VVDexOps deploy path (169 only).
